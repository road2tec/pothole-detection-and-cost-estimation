# Power BI analytics

This folder contains everything needed to build the Power BI report for the pothole register:
a documented star schema, Power Query scripts, DAX measures, a report-building guide and a theme.

> **No `.pbix` file is included.** Power BI Desktop is not available in the environment where this
> project was built, so a report file could not be created or validated. Renaming another file to `.pbix`
> would not produce a working report. Instead, the model below is fully reproducible in about 30–45 minutes.
> The DAX and M code here has **not** been executed in Power BI; validate it with the checklist in
> `report-design/report-guide.md` after building.

| Folder | Contents |
|---|---|
| `schema/` | `star-schema.md` (tables, columns, grain), `relationships.md` (what to create and what never to create) |
| `measures/` | `measures.dax` — all required measures with correct distinct counting and once-per-visit mobilisation |
| `power-query/` | `00-parameters.pq` (parameters + loader function), `01-tables.pq` (one query per table, typed) |
| `report-design/` | `report-guide.md` (pages, visuals, formatting, validation), `roadsight-theme.json` |
| `exports/` | Output of `npm run export:powerbi` (CSV files are git-ignored) |

## 1. Get the data

Two supported ways — pick one with the `Source` parameter.

**A. CSV export (works everywhere, manual refresh)**

```bash
npm --prefix server run export:powerbi          # live records only
npm --prefix server run export:powerbi -- --demo   # include labelled demo records
```

This writes the eight star-schema CSVs and `export-manifest.json` (reconciliation checks) to `powerbi/exports/`.
Engineers and administrators can also generate and download an export from the application's **Power BI** page.

**B. Live data feed (scheduled refresh)**

The API serves the latest export as CSV at
`GET /api/v1/analytics/powerbi-export/latest/<Table>.csv` (regenerated automatically when older than 15 minutes).
Authenticate with a read-only API key in the `X-Api-Key` header — create one on the Power BI page (administrators).
Keys can read analytics exports only and can be revoked at any time.

For refresh in **Power BI Service**, Microsoft's cloud must reach that URL: deploy the API on public HTTPS, or install
an on-premises data gateway in your network. This project does not assume a gateway exists and does not connect
Power BI to MongoDB directly.

## 2. Build the model

1. *Transform data → Manage parameters*: create `Source`, `BaseUrl`, `ApiKey`, `ExportDir` (see `power-query/00-parameters.pq`).
2. Create a blank query `fnLoadTable` with the function in `00-parameters.pq`.
3. Create one blank query per table from `power-query/01-tables.pq`, named exactly `FactPothole`, `FactRepairVisit`,
   `DimDate`, `DimRoad`, `DimArea`, `DimSeverity`, `DimStatus`, `DimModelVersion`. Optionally add `BudgetTarget`.
4. *Close & apply*, then create the relationships in `schema/relationships.md` and mark `DimDate` as the date table.
5. Create a `_Measures` table and add every measure from `measures/measures.dax`.
6. Build the pages in `report-design/report-guide.md` and apply `roadsight-theme.json`.
7. Validate totals against the application's Analytics page.

## 3. Why the model looks like this

- **Mobilisation once per visit.** `FactPothole[EstimatedCost]` is material + labour only. Mobilisation lives in
  `FactRepairVisit` (one row per real or provisional visit). The `Mobilisation Cost` measure sums it once for each
  distinct visit present in the current filter — the same rule the application uses — and there is no fact-to-fact
  relationship that could repeat it on every pothole.
- **Unique vs frame-level.** One `FactPothole` row per physical pothole; `FrameDetections` holds the number of
  video-frame observations, so "total detections" and "unique potholes" are separate, labelled measures.
- **Blanks are not zeros.** Unmeasured potholes have blank dimensions and cost, so averages and totals are not
  dragged down by invented zeros.
- **Configuration traceability.** `CostConfigVersion` and `ModelVersion` are on every row.

## 4. Optional: Power BI Service integration in the application

Set in `server/.env` (all optional — the application works without them):

| Variable | Purpose |
|---|---|
| `POWERBI_SECURE_EMBED_URL` | "Secure embed" link of the published report. The Power BI page shows it in an iframe; viewers sign in with their own Microsoft account. No embed token is generated by this server. |
| `POWERBI_TENANT_ID`, `POWERBI_CLIENT_ID`, `POWERBI_CLIENT_SECRET`, `POWERBI_WORKSPACE_ID` | Service principal used **server-side only** to verify the configuration |
| `POWERBI_DATASET_ID` | Enables "Refresh dataset now" and refresh history |
| `POWERBI_REPORT_ID` | Verified on the status check |

The tenant must allow service principals to use Power BI APIs, and the app registration must be a member of the
workspace. This integration has been implemented against Microsoft's documented REST API but **has not been tested
against a real tenant** in this environment. The status card only shows "Connected" after Microsoft actually responds.

## 5. Known differences from the application

- Monthly budget: if one work order's potholes were detected in different months, DAX counts its mobilisation in each
  month; the application attributes it to the first month. Overall totals are identical.
- The export reflects the database at export time; the application is live.
